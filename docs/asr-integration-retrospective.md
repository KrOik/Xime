# ASR 嵌入 Xime 的复盘与重做方案

## 1. 结论

这轮工作的主要问题不是“CI 修改得不够多”，而是把**能够编译**误当成了**已经接入输入法**。ASR 真正可用至少要贯通以下链路：

`设置与凭据 → 引擎选择 → 录音采集 → 流式协议 → partial/final 事件 → composing/commit → 停止、取消与异常恢复`

提交历史表明，这些环节没有在第一次实现前被定义成一个可验收的契约，而是在 CI 暴露编译问题、界面无法选择、语音栏无法识别服务商、中间结果提前结束语音模式后逐项补齐。因此，CI 只能证明特定环境中的静态构建结果，不能证明服务端凭据可用、WebSocket 协议正确，也不能证明文字最终进入当前编辑器。

如果重来，应先做一个仅包含 Android 端、单一服务商、单一音频格式的最小纵向切片，在真机上验证“一句话从麦克风变成已提交文本”，再扩展设置、自动凭据、更多事件和体验优化。

## 2. 从提交历史看到的问题

本轮 DouType 接入从 `6b90142` 到 `d6bd1a9` 连续经过七次提交：

| 提交 | 补上的环节 | 暴露的问题 |
| --- | --- | --- |
| `6b90142` | 初始 ASR 接入 | 一次加入约 4,100 行 `asr/` Python 工具及很薄的 Android 实现，范围过大，但关键 Android 链路尚未闭环 |
| `aa81ba5` | 自动注册与凭据 | 初版没有先解决运行时鉴权，编译成功也无法建立有效会话 |
| `fd505e0`、`ce22a02` | 远端编译与 OkHttp URL 兼容 | 本地依赖版本与 CI/主干实际版本没有在实现前对齐 |
| `516f986` | 功能开关、服务商选择、设置 UI、较完整协议 | 初版“有后端类”但用户无法完整配置和选择，协议实现也不足以工作 |
| `b070649` | 语音栏与输入法服务识别 DouType | 引擎已存在，但没有完整接入 Xime 的显示和路由判断 |
| `d6bd1a9` | 区分中间结果与最终结果 | 没有预先定义流式事件语义，partial 被当作 final，导致语音模式提前退出 |

由此可以归纳出几个根因：

1. **从外部实现出发，而不是从 Xime 的 `AsrBackend` 契约出发。** `asr/` 下的 Python 包不能在 Android 应用内直接运行；把参考实现放进仓库不等于嵌入 Xime。
2. **首个提交跨度过大。** Python 服务、Android 后端、设置页、协议、凭据本应拆成可独立验证的阶段；大提交使“代码存在”和“链路可用”难以区分，也违反最小修改精神。
3. **没有先画清状态机。** `partial`、`final`、服务端流结束、用户松手、取消和错误是不同事件。它们一旦混用，就会出现 composing 文本重复、最终文本丢失或界面提前退出。
4. **CI 被当成产品验证。** CI 通常没有麦克风、输入法 `InputConnection`、真实服务凭据和稳定的外部 WebSocket，因此只能承担编译、单测和协议夹具测试。
5. **配置、可用性和选择是三套状态。** “启用 STT”“选择在线/本地”“选择 DouType/FunASR”“凭据就绪”必须一致；只添加一个布尔开关或一个后端类都不够。
6. **过早复制了大量非运行时资产。** 独立 Python CLI、HTTP 服务、NLP 等能力不属于 Android 输入法的最小 ASR 集成面，增加审查、维护和安全负担。

## 3. 如果重来：ASR 应以什么形式加入

首选形式是：**Xime 内部的原生 Kotlin 流式后端，实现现有 `AsrBackend` 接口，通过受支持的公开服务端 API 工作。**

推荐保持三层边界：

1. `SpeechRecognitionManager` 只负责录音、后端生命周期和统一回调，不感知某家协议。
2. 每个服务商实现一个 `AsrBackend`，内部再把凭据、WebSocket 编解码和事件解析拆开，但不把服务商判断散落到输入法 UI。
3. `VoiceRecognitionHandler` 只消费统一事件：partial 更新 `setComposingText`，final 先结束 composing 再 `commitText`，错误或取消负责清理现场。

不建议把 Python ASR 服务直接“嵌入” APK。若 Python 项目确实是服务端，则应把它部署成独立、版本化的 HTTPS/WSS 服务，Xime 只保留公开客户端协议；它不应作为无法被 Android 运行的源码目录来代表集成完成。若目标是隐私优先和离线能力，则继续使用 sherpa-onnx 这类本地 JNI 后端，模型按 ABI、体积和设备性能单独管理。

## 4. 推荐的重做顺序

### 阶段一：先固定契约和验收样例

- 明确输入音频：16 kHz、单声道、PCM 16-bit little-endian；确认服务端是否需要固定帧长、序号和结束帧。
- 明确统一事件：`Connecting`、`Listening`、`Partial(text)`、`Final(text)`、`Error`、`Closed`。
- 明确结束规则：用户松手只发送结束帧，收到 final 或明确超时后才退出语音模式；取消不得提交文本。
- 写出一个真机验收样例：长按语音键说一句话，界面显示中间结果，松手后同一句话只提交一次。

### 阶段二：做最小纵向切片

- 只接一个公开、稳定、授权明确的在线 ASR 服务。
- API Key 先由设置页显式配置，不先做自动注册、设备伪装或复杂密钥交换。
- 仅支持 PCM，不做 Opus、多 pass、热词和格式化。
- 先接到已有服务商枚举、`SpeechRecognitionManager` 和 `VoiceRecognitionHandler`，确保从设置到输入框闭环。
- 在至少一台 Android 真机和两个普通编辑器中验证；输入法行为不能只靠 JVM 测试推断。

### 阶段三：补自动化验证

- 对协议编码和服务端消息解析使用固定二进制/JSON 夹具，覆盖 partial、final、错误和乱序/重复消息。
- 对后端使用假的 WebSocket 传输，验证 `start → audio → finish → final` 以及取消、超时、断线重连。
- 对 composing/commit 逻辑使用假的 `InputConnection`，断言 partial 不提交、final 只提交一次、cancel 不提交。
- CI 只使用 mock 服务和无密钥测试；真实服务连通性放到受控的手动或定时 smoke test，不能成为普通 PR 的必要条件。

### 阶段四：再补产品化能力

- 增加凭据过期刷新、限流提示、网络切换、超时与可取消重试。
- 增加供应商能力参数、隐私说明、流量提示和日志脱敏。
- 最后再考虑 Opus、热词、自动标点、服务商降级和更多设置项；每项仍作为独立功能点验收。

## 5. 必须特别注意的内容

### 协议与状态

- 不要用“收到非空文本”判断结束；必须以服务端明确 final 标记或结束事件为准。
- WebSocket 建连成功不代表 ASR 会话就绪。音频只能在鉴权和会话初始化确认后发送，否则需要有界缓冲。
- `finish`、`cancel`、`close` 必须分开：finish 等最终结果，cancel 丢弃结果，close 释放资源。
- 防止重复 final、迟到回调和旧会话回调污染新会话，可为每次识别分配 session id。
- 当前后端若被设置切换，应释放并重建；不能继续复用旧供应商实例。

### Android 输入法集成

- 麦克风权限、`AudioRecord` 初始化失败和后台录音限制都要给用户可理解的反馈。
- partial 使用 composing 区，final 只能提交一次；开始新会话、取消、切换应用或切换输入法时都要清理 composing。
- 不要在主线程进行凭据交换、网络连接或等待线程结束。
- 录音振幅、静音检测和预录音应与发送给后端的音频一致；当前“检测到说话前不发送音频”的策略可能截掉句首，应保留短环形预缓冲。
- 覆盖短按、长按松手、无声、快速取消、网络中断、横竖屏/界面重建和编辑器切换。

### 安全、隐私与合规

- 语音是敏感数据。设置页应明确在线上传的服务商、用途、保留策略和隐私政策，并让用户主动启用。
- API Key、token、设备标识不得写入日志、仓库或普通明文偏好；使用 Android Keystore 加密，并支持清除。
- 当前 DouType 凭据流程模拟第三方包名与 User-Agent，并从非公开配置接口获取产品密钥。即使技术上可工作，也存在接口随时失效、授权边界、服务条款、隐私和应用商店审核风险。正式产品不应依赖这种方式；应使用官方开放 API 或自有、合规的服务端凭据代理。
- 不要把长期服务端密钥下发到客户端。若必须代理，应使用短期、限权限、可撤销的会话令牌，并在服务端做配额和滥用控制。
- 日志只记录状态码、阶段和 request id；不得记录音频、完整转写、密钥或可关联设备身份。

### 构建与发布

- 在线 Kotlin 后端不应依赖仓库中的 Python 包才能构建；若两者都保留，应明确它们是不同部署单元并分别维护。
- 本地 ASR 要验证每个目标 ABI 的 JNI 库、模型兼容性、APK 体积、首次下载校验、低内存释放和混淆规则。
- 依赖升级（尤其 OkHttp）应以主干锁定版本编译，不要为通过某次 CI 临时适配多套未经测试的 API。
- CI 门禁应包括 Android 编译、单元测试、协议夹具测试、secret 扫描和 release 混淆构建；真实语音质量仍需设备测试矩阵。

## 6. “完成接入”的定义

以后只有同时满足下列条件，才能称为 ASR 已嵌入 Xime：

- 用户能在设置中选择、配置并明确启用该服务商，状态显示与实际选择一致。
- 真机能从麦克风发送音频并得到 partial 与 final。
- partial 只更新 composing，final 只提交一次；取消、错误和无声不产生脏文本。
- 结束、超时、断网、切换应用和连续两次识别均能恢复到可再次使用的状态。
- 凭据和日志符合安全要求，服务 API 的使用获得正式授权。
- 自动化测试覆盖协议和输入法文本生命周期，CI 构建通过。
- 至少完成一次受控真机端到端验收，并记录应用版本、设备、Android 版本、服务端环境和测试结果。

## 7. 最重要的经验

ASR 集成应以“用户的一句话是否可靠地只进入输入框一次”为中心，而不是以新增了多少后端代码、设置页面或 CI 修复为中心。先定义事件契约，做最小端到端切片，再分别扩展协议、凭据和体验；CI 是这个过程的护栏，不是终点。
